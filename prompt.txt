# 1. PROJECT

Build a complete desktop settings application named:

**ZETTINGS**

for:

**Zyntrix OS**

Zyntrix OS is based on:

**Kubuntu + KDE Plasma**

ZETTINGS will eventually serve as the primary system settings application for Zyntrix OS.

This is NOT intended to be a direct clone of Windows Settings, macOS System Settings, KDE System Settings, GNOME Settings, or any other existing application.

Study existing operating systems to understand their information architecture, usability, and engineering principles.

Then create an original experience.

# 14. BACKEND ARCHITECTURE

Flutter is responsible for:

* UI
* navigation
* presentation
* state management
* user interaction

System-level functionality must be isolated behind a backend abstraction.

Preferred architecture:

```text
Flutter UI
    ↓
Application Services
    ↓
Platform/System Abstractions
    ↓
Rust System Backend
    ↓
D-Bus / Linux APIs
    ↓
KDE / systemd / NetworkManager / PipeWire / etc.
```

Use Rust for privileged or security-sensitive system operations where appropriate.

Flutter must never directly execute arbitrary shell commands for normal settings operations.

---

# 15. RUST BACKEND

Where Rust is used, maintain strict separation between:

* IPC
* system services
* permissions
* repositories
* domain logic
* hardware discovery
* system adapters

Use typed APIs.

Avoid passing arbitrary command strings between Flutter and Rust.

Prefer explicit commands such as:

```text
get_display_configuration()
set_display_scaling()
get_network_interfaces()
set_wifi_enabled()
get_audio_devices()
set_default_audio_device()
```

rather than:

```text
execute(command)
```

# 17. PERMISSIONS

Use least privilege.

Normal settings should operate without administrator privileges whenever possible.

When elevated privileges are genuinely required:

1. explain why
2. request authorization through the appropriate Linux mechanism
3. perform only the required operation
4. never run the entire application as root

Use PolicyKit where appropriate.

Never request unnecessary privileges.

---

# 18. SECURITY

Follow:

* least privilege
* capability-based access
* input validation
* secure IPC
* permission validation
* safe error handling
* auditability

Never:

* execute arbitrary user-provided shell commands
* concatenate untrusted input into shell commands
* run the application as root
* bypass PolicyKit
* disable system security mechanisms
* store credentials insecurely

---

# 19. STATE MANAGEMENT

Use a predictable state architecture.

Separate:

```text
UI state
Application state
Settings state
System state
Persistent preferences
```

Do not allow widgets to become responsible for system-level business logic.

Avoid unnecessary global mutable state.

Settings changes should follow a predictable flow:

```text
User interaction
      ↓
Intent
      ↓
Application service
      ↓
System backend
      ↓
System result
      ↓
State update
      ↓
UI
```
